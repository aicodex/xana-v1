# 组件化、独立评测与长期迭代主目标

> 本文记录 Xana 后续的主要目标。不是一次局部功能说明，而是后续架构、测试、评测和迭代工作的共同方向。具体公共接口仍需逐项设计并经用户审批。

## 1. 北极星目标

Xana 不再只是一个 toy 或单项目脚本，而要成为一套**可上线、组件化、模块化、可独立测试、可持续打磨的 Agent 系统**。

拆模块的直接目的不是代码整洁，而是让后续迭代可以：

1. 单独替换 harness、memory、tools 等组件或其中的策略；
2. 单独运行组件测试，快速定位回归；
3. 在真实模型和长程任务上持续比较候选版本；
4. 保存完整证据、评分与问题分析，决定保留或回滚；
5. 让不同开发者在明确的边界上并行工作。

最终目标是形成一个长期运行、评测驱动的迭代系统，而不是依靠一次性 prompt 调整或主观体验判断好坏。

## 2. 为什么需要组件化

后续重点迭代对象包括：

- harness 本身的组件：执行循环、上下文、压缩、恢复、任务调度、事件和状态；
- memory：写入、长期整理、反思、召回、冲突处理和隔离；
- tools：输入输出契约、执行、错误处理、取消、权限和结果转换；
- 与它们连接的前端、服务、沙箱和评测设施。

如果这些能力只能通过完整系统黑箱测试，就无法回答“这次提升究竟来自模型、prompt、检索、工具还是 harness”。因此组件边界必须支持独立构造、独立调用、独立记录和独立评分。

## 3. 模块与职责

### 3.1 Harness SDK

负责：

- 单 turn 与多 turn 执行；
- 模型请求与流式事件；
- 工具循环和 run 生命周期；
- queue/steer/cancel；
- compaction、恢复、预算和验证；
- 后台任务与定时调度；
- 状态、usage 和 trace 交付。

Harness 的独立评测不应依赖某个具体 memory 或 tool 实现。可以使用 scripted model、固定工具和固定状态构造单 turn 场景，验证“这次工具选择是否正确、参数是否正确、结果处理是否正确、状态是否正确提交”。

### 3.2 Memory

Memory 不再被视为单一检索器，至少拆成以下职责：

- **写入策略 / 提示词注入**：决定哪些内容值得自动写入、何时询问、哪些内容不写入；
- **Dream / 每日整理**：对一段时期的记录做归纳、去重、合并、过期和主题整理；
- **反思**：从错误、失败、用户纠正和评测反馈中形成可复用经验；
- **用户明确要求**：用户说“记住/不要记/忘掉/更正”时走明确、可验证的路径；
- **检索**：词项、语义、证据评分、多跳扩展、时间和冲突处理；
- **快照与隔离**：复制、fork、删除、项目/会话隔离和索引重建；
- **用量与观测**：评分调用、token、延迟、写入和召回轨迹。

这些职责共享数据契约，但可以用不同实现。提示词或策略不应寄生在某个具体检索后端里。

### 3.3 Tools

负责：

- ToolSpec、输入 schema 与输出契约；
- validate、permission、execute、cancel、render；
- 超时、重试、错误分类和资源清理；
- MCP 工具的发现、审核、发布和故障摘除；
- 面向评测的录制、回放、故障注入和环境策略。

工具必须能不启动完整 Agent，直接以 `ToolInvocation + ToolContext` 做独立测试。

### 3.4 Sandbox

负责文件、进程、网络、凭据、资源和副作用边界。需要独立验证：

- 路径逃逸与符号链接；
- 进程组清理和超时；
- 网络访问控制；
- secret 泄漏；
- CPU/GPU/内存/磁盘预算；
- 容器退出和状态恢复。

沙箱不是附属于某一道 benchmark 的环境配置，而是可独立测试的系统组件。

### 3.5 前端与服务

前端是状态与控制的投影，不拥有另一份执行状态。

- REST/SSE 或后续协议只承载公开契约；
- 页面不直接访问内部服务定位器；
- 内存与远程 transport 应运行同一套 conformance 测试；
- 前端可独立测试加载、刷新、断线、审批、取消、历史与错误状态。

### 3.6 评测设施

评测本身也视为需要测试的软件模块，包括：

- suite 与样本格式；
- runner、调度、预算、并发和隔离；
- tape 录制与回放；
- scorer 与判分版本；
- 结果存储、比较、问题分类和报告；
- 防改题、防污染、heldout 与来源追踪。

评测代码出错、样本改变、模型/judge 版本改变，都必须能被识别，不能静默混入历史结果。

## 4. 稳定接口与可演进注入点

### 4.1 稳定 SDK 接口

接口用于连接模块，关注：

- 输入输出数据结构；
- 生命周期和调用顺序；
- 错误类型与失败语义；
- 并发、取消和超时；
- 持久化、恢复和资源所有权；
- 事件流与状态投影；
- 安全边界。

公共接口的新增、删除、改名、字段语义、默认值、事件顺序、取消语义等变化，**必须由用户明确审批**。审批后应原位迁移调用方并删除被替代入口，不长期保留 v1/v2 双路径。

### 4.2 注入点与策略规约

有些扩展点不应过早冻结成永久 SDK，而应作为有版本、有测试、可替换的规约：

- 何时自动写记忆；
- dream 的触发与整理策略；
- 反思的触发与证据要求；
- 记忆检索、评分和冲突裁决；
- prompt 片段与注入位置；
- compaction 的保留策略；
- 停止、验证和续跑策略；
- 工具选择、延迟披露和错误恢复策略；
- 调度、预算和长期运行策略。

它们仍需明确输入输出、版本和证据，但可以根据评测结果演进。接口与策略不能混成一段无法替换的实现。

## 5. 独立测试与评测

### 5.1 测试层级

每个模块至少按需要覆盖：

- 单元测试；
- 公共契约测试；
- 集成测试；
- 边界值与非法输入；
- 并发、取消与资源清理；
- 故障注入；
- 压力与长程运行；
- 安全与越权；
- 历史回归；
- 性能、token 和成本。

“能启动”或“跑通一个 demo”只属于 smoke，不能作为上线或采用候选版本的依据。

### 5.2 Memory 独立评测

Memory 不携完整 harness 也可以评测。使用固定记忆集、固定查询、固定评分器和固定时间，分别测试：

- 应写入/不应写入；
- 用户明确要求与更正；
- dream 合并与去重；
- 错误反思是否有证据；
- 检索准确性与无关注入；
- 新旧事实冲突；
- 删除、过期与拒答；
- 跨项目、跨会话隔离；
- 快照复制与索引重建；
- 延迟、调用数与 token 成本。

最终采用指标而不是只展示成功例子，例如 Recall@k、Precision@k、冲突解决率、旧事实误用率、重复条目率、无依据回答率、延迟分布和成本。

### 5.3 Tools 独立评测

固定 invocation 与环境，直接检查：

- 正常输出与边界值；
- 错误类型和用户可读结果；
- 超时、取消、重试与副作用；
- 大输出、二进制、非法 schema；
- 权限、沙箱和 secret；
- MCP 断连、重连、审核和重审；
- 相同输入的回放一致性。

### 5.4 Harness 独立评测

Harness 可以不依赖真实模型：

- scripted model 发出固定工具调用；
- 固定工具返回正常/错误/超时结果；
- 验证模型下一轮收到的内容；
- 检查历史、事件顺序、usage、取消和终态；
- 检查单 turn 是否正确结束；
- 检查 queue/steer、compact、恢复与 goal 状态。

另设真实模型场景评估模型与 harness 的联合表现，但不把它当作组件机制的唯一验证。

### 5.5 历史故障回归

过去真实出现的错误应转化为最小可复现样本：

1. 保存当时的输入、prompt、工具 schema、模型响应、工具结果和环境状态；
2. 能精简时保留最小必要上下文；
3. 分别验证修复前失败、修复后通过；
4. 后续每个相关候选版本都重放；
5. 记录修复是否引入新的重复调用、性能或成本退化。

## 6. Tape、评分与问题分析

### 6.1 原始证据

每次运行尽可能保存：

- 任务与样本 ID、split、seed、repeat；
- 代码 commit、依赖锁、配置和 Docker 镜像；
- 模型/provider/版本/推理参数；
- prompt、system、注入片段和工具 schema 的版本或内容哈希；
- 原始模型请求与响应；
- 工具调用、参数、结果、错误、时间和用量；
- memory 快照、索引版本和评分后端；
- checkpoint、取消、恢复、超时和终态；
- 最终产物、官方或本地 verifier 结果。

原始记录使用版本化 JSONL/目录结构，尽量只追加；派生分析和报告不得覆盖原始证据。

### 6.2 评分纪律

- 优先确定性 scorer；模型 judge 是独立版本化依赖，不与被测对象混为一谈。
- 固定模型、任务、预算、工具和判分条件做配对比较。
- 保留多个 seed/repeat，报告样本数和波动，不把单次运行当成稳定提升。
- heldout 不回流给迭代者；评分代码和真值的变更会使旧缓存失效。
- 同时记录结果分、机制指标、资源成本和副作用。

### 6.3 问题分析

失败不是只有一个分数。每个重要失败应尽量归类到：

- 需求理解；
- 方案/规划；
- 工具选择或参数；
- 工具执行；
- 记忆写入或召回；
- 上下文丢失；
- 重复探索/死循环；
- 自我验证不足；
- 提前终止；
- 预算/超时；
- 沙箱/权限；
- 基础设施；
- 无法可靠分类。

每类保留代表轨迹和最小复现，后续迭代针对机制而不是只针对单题答案。

## 7. 长期运行与多模型资源

本地闲置 GPU 可以部署 Qwen 27B/9B、GLM-5.3-Flash 或其他模型，组成长期运行的候选工作池。设计上应保证：

- 每个 trial 有独立 workspace、配置、记忆快照和日志；
- 模型、模型服务、容器和 GPU 资源有明确所有者；
- 资源不足时排队，不静默切换模型；
- 长任务有预算、checkpoint、超时收尾和清理；
- 同一模型可比较不同组件/策略，同一组件也可比较不同模型；
- 结果按 `(model, harness, memory, tools, policy, suite, seed)` 标识，不能混为单一“模型分数”。

长期运行可以形成多候选并行评测，但共享资源调度不能污染各候选的状态与评分。

## 8. 迭代闭环

```text
提出一个组件或策略变更
        ↓
运行单元/契约/历史回归
        ↓
运行该组件的独立评测
        ↓
运行集成与端到端配对对照
        ↓
必要时进行长程、多 seed、压力测试
        ↓
分析结果、成本、副作用和失败类型
        ↓
保留 / 继续修改 / 回滚，并留下账本
```

优先一次只改变一个主要变量。无法解释的提升先查基础设施、污染和判分，不直接采用。

## 9. 实施顺序

1. 盘点现有接口，分类为公共 SDK、内部 SPI、策略规约和实现细节。
2. 建立接口清单、所有权、审批记录和公共契约测试。
3. 建立统一 tape/trace/score/result 格式以及评测设施自身测试。
4. 先让 memory、tools、harness 能独立构造与评测。
5. 建立历史故障样本库和固定基线。
6. 接入多模型、容器和长程调度，形成持续分析报告。
7. 在证据充分后逐项替换实现，不保留重复入口。

## 10. 非目标

- 不把组件化变成每个函数一个 ABC。
- 不为了“统一”而抹平不同 provider 或后端的语义差异。
- 不把端到端模型评分当作组件正确性的替代。
- 不靠模型自觉维护状态、记忆或测试纪律。
- 不保留长期并行的旧新接口来规避迁移。
- 不在没有证据时把某个实现称为生产稳定或评测有效。

## 11. 待审批事项

本文只批准目标与方向，不代表任何具体公共接口已获批准。后续需要单独提交：

- 公共接口清单及每个接口的状态；
- Memory、Tools、Harness 等最小接口集合；
- 注入点/策略的版本与审批边界；
- tape/score/result 的数据格式；
- 迁移顺序、删除范围和验收标准。

具体接口变动必须由用户明确批准后才能实施。

## 12. 当前边界裁定

这些决定用于消除后续设计歧义，不代表具体接口已经获批：

1. **与 extension_api 的关系**：现有 Contributor ABC、ExtensionRegistry 和 capabilities 是组件化需要收敛的 provider/extension SPI，不另起一套扩展体系。并非所有内部 hook 都自动成为稳定公共 SDK；公共使用面与实现扩展面分别盘点，变动仍须审批。
2. **上线形态**：当前以个人/单用户、单项目 serve 为主要运行边界，不引入外部多租户语义。研发评测资源池与正式项目运行分开；项目隔离、凭据和沙箱要求不因此降低。
3. **Memory 默认归属**：默认是当前项目，项目之间不隐式共享。会话级或用户级共享必须显式声明；快照/fork 必须保留来源和作用域，不能复制后误写原项目。
4. **迁移方式**：以为最终契约服务为准，可以重写组件内部实现，但默认原位迁移调用方、测试和数据，不为保留旧实现而长期增加 v2/compat 路径。历史数据优先一次性迁移，不擅自删除。
5. **策略采用**：候选策略必须先有测试、评分和分析记录；在没有另行批准自动采用策略前，不因为分数较高就自动替换生产策略。保留候选、证据和回滚依据。
6. **Transport 范围**：内存与 daemon/远程 transport 对同一公共 facade 跑共享 conformance 测试。Web、CLI、聊天渠道可以使用各自的展示适配，但不能因此创建另一份执行状态或另一套业务语义。
7. **审批身份**：本文所称“用户审批”指项目所有者对公共接口或治理规则的明确确认，不把测试自动通过、模型判断或 agent 自审批当作接口批准。
