# 记忆三层:记录 → 做梦整理 → 分类记忆与技能

## 1. 问题

- 现在写记忆要当场想好名称、描述、类型(`memory_write create`),记的成本高;用户随口说的规则容易不记或记得零散。
- 记忆只有 4 种类型,没有主题;同一类做法(估值、产业链调研、横向对比)散在多条记忆里,召回靠每条的描述碰运气。
- "怎么做某类事"的规则(例:引用卖方预期至少打 8 折、用上下游业绩推算、警惕积压订单一次性确认、选股看预期差)本质是**做法**,适合在做那类事时整体加载,而不是每句话去挑。
- 没有整理:重复、矛盾、过时的记忆会越积越多。

## 2. 参考(源码调研,2026-10-19)

| | 粗记 | 整理 | 分类 / 抽象 | 召回 |
|---|---|---|---|---|
| Claude Code | 每轮结束后台分出子 agent 提取记忆(`services/extractMemories`);助手模式下先写只追加的每日日志 | `services/autoDream`:距上次 ≥24 小时且 ≥5 个新会话时,后台整理 agent 四步:看现状 → 从日志 / 对话记录找新信号 → 合并进主题文件、修正被推翻的事实、相对日期改绝对 → 修剪索引(≤200 行) | 主题文件 + 4 种类型 | 索引常驻 + 每轮快速模型挑选 |
| Codex | 会话结束后把整段对话总结成一条原始记忆(按任务拆分,标成败与关键词;"不写比乱写好") | 会话启动时后台:整理 agent 把原始记忆合并进 `MEMORY.md`,工作区用 git 记差异,按差异增量更新 | 按"任务组"(项目 / 工作流)分组,另有用户偏好、可复用知识、失败教训;**反复出现的做法升级为技能** | 摘要索引常驻(≤2500 token),模型按关键词再翻全文 |
| OpenClaw | 每日笔记 `memory/YYYY-MM-DD.md`;上下文压缩前静默追加 | 每晚 3 点 dreaming:浅睡 / REM / 深睡打分(被搜次数、相关度、跨天数),高分晋升进 `MEMORY.md` | 规则公式打分,不调模型,没有真正的抽象 | `MEMORY.md` 常驻 + 最近两天笔记 + 混合检索工具 |
| Hermes | 模型随手记;每 10 轮后台复盘补记 | 记忆不整理(两个小文件,满了模型自己替换);每周"管理员"把零散**技能**合并成大类技能,长期不用的归档 | 做法一律进技能,技能按大类合并 | 两个文件常驻;技能列表常驻,全文按需加载 |

共同点:**记录与整理分开**(记录要便宜,整理在后台慢慢做);**做法进技能**(Codex、Hermes)。

## 3. 设计

### 3.1 第一层:记录(主动记 + 后台提取)— 已实现(2026-10-19)

照 Claude Code:**主模型主动记**(系统提示词写清各类"什么时候存")+ **每轮后台提取**兜底(`services/extractMemories`)。

- **主动记只给用户在线的聊天会话**:系统提示词的"记忆"段分两部分。`MEMORY`(记忆在哪、会自动看到什么、可能过时、后台会补记)给所有有 memory 工具组的 agent;`MEMORY_SAVING`(四类各在什么时候存,含"纠正和认可都要记,写明原因与适用场景""描述写清在什么情况下有用""同类用同一个主题")只给交互会话(`PromptProfile.mode == "interactive"`)。
- **后台提取给所有运行**:聊天会话、定时任务、以后的长期运行 agent(无人值守)都跑;`agent_run` 派出的子 agent 不跑(请求带 `parent_run_id`,它的任务来自主 agent,用户的话已在主会话里提取)。
  - 时机:一轮正常结束(final)后,harness 把本轮(用户消息起到最终回答)交给 `ModelMemoryExtractor`,后台任务执行,不影响回复。本轮模型已经自己调过 `memory_write` 就跳过。
  - 提示词(`runtime/memory_extract.py`,改写自 CC extractMemories 与各类型的"什么时候存",加 Codex 的"宁可不记"):输入已有记忆索引 + 本轮记录(工具结果截断到 300 字,总长 ≤12000 字);交互会话重点看用户的纠正、偏好、规则与理由,无人值守运行重点看执行中的经验(有效做法、踩过的坑、环境与数据源事实)。输出 JSON。
  - 写入只有两种:新建一条记忆,或追加到已有记忆后面;文件名已存在或与已有记忆的名称 + 描述相似度 ≥0.6 时改为追加。**不改写、不删除**。每轮最多写 3 条。
  - 频率:`memory.extract_every`(默认 1 = 每轮;N = 每个会话每 N 轮;0 = 关闭)。选择模型同召回(`model_tiers.fast` 或当前模型),关闭思考。
- 记忆 frontmatter 新增可选 `topic`,索引按 类型 → 主题 分组(无主题的排在该类型最后);`memory_write` 支持 `topic`。
- 原设计的"粗记日志"(`memory_write note` + 日志注入)暂不做:后台提取直接写分类记忆,做梦实现前也能被召回;日志在做梦实现时再评估是否需要。

### 3.2 第二层:做梦整理

- **内置 agent `dreamer`**:提示词改写自 Claude Code `autoDream` 的 consolidation prompt,并加入 Codex 的分组方式与"不写比乱写好";无人值守。工具:Read / Glob / Grep(读记忆、技能、本项目会话记录)、`memory_write`、`skill_propose`、`notify_user`;没有 Bash、联网和通用 Write / Edit。
- **何时做梦**:
  - 定时:用户开启后建一个静默定时任务(每天凌晨,agent = dreamer,结果送回开启它的聊天);dreamer 先看整理状态,自上次以来没有新日志、也没有新会话就直接结束。
  - 手动:用户说"整理一下记忆"时委派给 dreamer。
  - 开关在 `memory` 技能 / 命令里:"开启记忆整理""关闭记忆整理""现在整理"。
- **整理步骤**(照 CC 四步):
  1. 看现状:记忆索引、现有技能列表、整理状态。
  2. 找新信号:上次整理后新增 / 追加的记忆;必要时按关键词在本项目最近的会话记录里查(不通读)。
  3. 整理:
     - 事实、偏好、项目约束 → 分类记忆(`memory_write` create / update):补类型、主题、描述,合并重复,修正被推翻的,相对日期改绝对日期。**直接生效**。
     - 做法(怎么估值、怎么找上下游、怎么横向对比……) → 合并进项目技能:同一类归进同一个技能,优先改已有技能,其次新建大类技能(不建"某只股票""某次报错"这种一次性技能)。**只提建议**(`skill_propose`),不直接写。
  4. 修剪:删掉被技能吸收、过时或错误的记忆;记忆总数与索引保持在上限内。
- **备份与记录**:每次做梦前把 `memory/` 与项目技能目录快照到 `memory/.dream/backups/<时间>/`(保留最近 10 次);整理结束写一份变更记录 `memory/.dream/reports/<时间>.md`(改了哪些记忆、提了哪些技能建议、依据是哪几条记忆)。

### 3.3 技能改动要用户确认

- `skill_propose`(只在无人值守会话可见,同 `notify_user`):提交一条技能建议(新建或修改哪个技能、完整的新 SKILL.md、改动说明、依据),存到 `memory/.dream/proposals/<id>.md`,不写技能目录。
- 做梦结束时若有建议,dreamer 用 `notify_user(kind="decision")` 发给用户:列出每条建议的标题与改动要点,选项"全部应用 / 逐条看 / 都不要"。
- `skill_proposals`(只在交互会话可见):`list` / `show <id>`(含与现有技能的差异)/ `apply <id>` / `reject <id>`。用户在聊天里答复后,主 agent 用它应用或拒绝;应用即写入项目技能目录并热加载。**应用只能发生在用户所在的交互会话里**,dreamer 没有这个工具。
- 建议 14 天无人处理自动作废(记入变更记录)。

### 3.4 第三层:分类记忆与技能

- 记忆 frontmatter 增加可选 `topic`(如"估值""产业链""选股",由 dreamer 或模型填),索引按 类型 → 主题 分组;召回的选择模型同时看到主题。其余与 [memory-recall-design](memory-recall-design.md) 相同。
- **项目技能**:加载 `<项目目录>/.xana/skills/*/SKILL.md`(现在只加载 `~/.xana/skills/`,项目里的技能实际没进列表);两级同名时项目级覆盖用户级。改为热加载(照 FileAgentRegistry:列表与 skill_load 前按 2 秒节流刷新,`skill_proposals apply` 后强制刷新),不用重启。
- 做法进技能后:平时只在技能列表里占一行,做那类事时 `skill_load` 全文;查价格、跑回测不加载,不占上下文。

### 3.5 例子:用户的四条投研规则

用户在聊天里分几次说了这四件事,模型主动记下,或由后台提取写成 feedback 记忆(主题:估值、选股)。当晚做梦:

- 识别为两类做法,提出两条技能建议:
  - **估值与业绩粗估**(新建):引用卖方 / 一致预期至少打 8 折,唱多机构越多越警惕(依据:今年因采信过于乐观的预期亏损);缺直接数据时用上下游或同行推算(交换机 ↔ 交换机 PCB);单季高增长先查是否积压订单集中确认。
  - **横向对比选股**(新建,或并入已有的选股技能):看预期差而非确定性;大白马预期差为 0、业绩不及预期会暴跌;业绩差但同行龙头大赚的,环比大增可能在业绩披露前先涨。
- 同时更新记忆:demo 的"项目定位与投研主流程"里"机构预期 8 折"那句改为指向新技能。
- 第二天早上用户收到"需要你决策"的通知,回"全部应用",两个技能生效。之后用户说"估一下某公司明年业绩",模型从技能列表里加载"估值与业绩粗估";说"查一下 000001 现价",不加载任何技能。

## 4. 实施顺序(每步可独立验证)

1. 项目技能目录加载 + 热加载(独立有用,也修掉 demo 技能不生效的问题)。
2. ~~日志 + topic~~ → 已实现:主动记(聊天会话)+ 每轮后台提取(所有运行)+ 记忆 `topic`(§3.1)。
3. `dreamer` agent、整理状态、备份与变更记录、手动触发。
4. `skill_propose` / `skill_proposals` 与确认流程。
5. 定时做梦的开关(静默定时任务)。

## 5. 不做

- 不用打分公式晋升(OpenClaw):这里要的是抽象归类,交给模型整理。
- 记忆的整理直接生效,不逐条确认(有备份与变更记录);只有技能改动要确认。

## 6. 验证

- 单测(记录层已覆盖:主动记只在聊天会话、后台提取的写入规则与跳过条件、topic 分组);项目技能加载、覆盖、热加载;`skill_propose` 只在无人值守可见、`skill_proposals` 只在交互可见;apply / reject / 过期;dreamer 的工具范围(不能写技能目录、不能联网);备份与变更记录。
- 端到端:用 fake 模型跑一次做梦,从两条 feedback 记忆得出一条记忆更新与一条技能建议;决策通知 → 主会话 apply → 技能出现在列表里。
- 线上:在 demo 里按 3.5 的例子走一遍,再分别问"估一下某公司明年业绩"和"查一下现价",看是否只在前者加载技能。
