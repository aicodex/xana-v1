# 会话、插话与取消：当前契约

一个会话只有一个活动 run。执行、对外观察和后台任务分别有明确的生命周期。
实现入口为 `harness_sdk/turn_control.py` 与 `harness_sdk/default.py`。

## 输入与执行

`TurnCoordinator` 是活动 run 和待处理输入的唯一权威。普通新消息在空闲时启动 run；
忙碌时按接收顺序写入同一持久队列（delivery=queue），返回绑定待启动回答的 `input_accepted`。
当前回答结束后，队列逐条启动独立 run，仍只允许一个执行；断开观察不会删除或停止已接收消息。
输入带稳定 `input_id`；接收和消费回执落盘，重试和重启不会重复记录同一条输入。

点击“立即插话”通过 `TurnCoordinator.promote(sid,input_id)` 将选中消息改为 delivery=steer。
其余消息继续排队，多个提升项仍按原接收顺序消费。提升只发 wakeup，不触发 AbortSignal；
在完整模型响应、完整工具结果批次之间写入主历史，不抢占正在生成的模型响应。
普通工具完成后先写回结果再处理插话，不终止普通命令，不重执行已完成工具。
`agent_run` 初次等待和 `task_wait` 可被插话唤醒，返回仍在运行的任务 ID，任务继续执行。

2026-11-10 已对照 Kimi 最新 `8dd3aa3789a21778261457bba5e56a758583e8c0` 复核：普通排队等整轮回答结束；“立即插话”仍先等当前模型响应/工具批次完成。其 `human/test/agent/machine.test.ts:1308` 验证 slow_tool 结果在提升消息之前进入历史；独立 steerSignal 仅供任务观察等待使用。Xana 本次复核无需改动此行为，10 项队列专项通过。

run 由服务持有；SSE、渠道交付或调用方观察流关闭，不会取消执行。
不同会话可以并行。运行期间使用启动时的模型、cwd 和工具配置快照；权限在工具执行前按会话最新选择判定。
`/model` 等更改从下一个 run 生效；插话不偷偷更换当前 run 的配置。

## 取消与卡片

停止按钮传递原 `(session_id, run_id)`。Web 绑定按钮显示时的活动 run，避免延迟请求误停队列下一轮。飞书按原卡找到会话；TG 用短摘要键定位原卡，避免
64 字节 callback 上限截断 run ID；CLI 同样发送原 run ID。旧按钮和跨会话按钮不能停止新 run。
`/cancel` 无参数仅请求停止当前 run，不设置“取消下一轮”的标志。

取消与插话使用不同信号。取消可结束无增量返回的模型读取，并停止当前 run 直接持有的工具；
写操作使用工具已有的协作取消和宽限收尾。已交出的后台任务用独立 `task_stop` 停止。
取消前已提升的插话随当前 run 收尾写入历史，不为这些插话额外推理。
尚未提升的排队消息仍按序启动后续 run；“停止回答”仅停止对应 run，不等于清空队列。
父回答取消后到达的后台结果保留到用户下一轮，不立即唤醒已停止的回答。

后台结果使用稳定输入身份，经同一持久队列或主历史提交后确认。自动通知保留来源，队列中
尚未消费的用户输入优先。空闲会话经同一准入启动处理结果的 run；接收回执与模型回答分开，
网关继续完成渠道渲染。临时子 run 和无人值守 run 通过事件等待其后台工作，不反复请求模型维持存活。
停止任务须等待实际执行收尾，重启不自动重放任务。完整契约见[后台任务](../../doc_ai/harness_background_tasks.md)。

飞书/TG 的排队卡提供“立即插话”按钮，通过原聊天和 input_id 定位，旧按钮不提升别的消息。
排队卡在实际启动时进入正常回答状态，提升后成为提示终态。
每个 run 对应一张回答卡，`turn_started` 开始，`final/error/cancelled` 直接进入终态。
停止请求显示收尾状态并撤掉停止按钮。压缩命令有自己的卡和独立取消信号。
不再存在后台回答按钮、attach/detach、异步模式开关、普通或压缩占位符。

## 历史与压缩

`HistoryMirror` 的有序主日志是持久化权威，`ContextSDK` 是可重建的运行时视图。
消息先写日志，再更新内存。run trace 是审计记录，不是第二份可写会话状态。

自动和手动压缩共用 `ContextSDK.compact`：冻结前缀及行 ID → 生成摘要 → 保存完整转录 →
持久替换该前缀 → 更新 SDK，保留冻结后追加的尾部。取消或提交前失败保持原历史。
提交期间取消必须等待磁盘和内存操作完成，避免完成一半。每 sid 一把压缩锁。
正常写入经 `ContextSDK.append_history`，恢复经 `ContextSDK.restore`；请求组装只读隔离快照，
嵌套工具参数也不与内部历史共享。不存在独立的压缩生命周期管理器。
忙碌时 `/compact` 排在同一 run 的安全边界，空闲时独占会话，期间新输入等待入场。

模型窗口、输出长度、压缩预留和缓存 TTL 的唯一推导仍在 `config/loader.py`：
完整配置 C/O 时 R=min(O,20000)，自动线 C-R-13000，阻断线 C-R-3000；
缺配置时自动线 C-64Ki，兜底预留不额外叠加 13k。缓存 TTL 默认 1h，按模型配置。
媒体引用、思考文本、已揭示工具清单随历史和摘要保留。

## 重启与迁移

启动按主日志重建 SDK，并把未完成 run 标为可恢复；不会自动重新发送原始任务。
`/resume` 只接受本会话已停止的 run，新 run 使用当前主历史；任何新 run 开始前，未配对工具结果都标为未知，
不直接重放副作用。原 run trace、压缩转录保留，完成记录不改名、不回填旧状态。
已确认接收但未消费的聊天输入（含 queue/steer 状态）由服务启动后的 `recover_inputs()` 逐项重建正式请求依赖，再按同一准入继续接入；
子 agent / 调度子会话输入保留，等待调用方显式恢复，不自动重新发起内部任务。

历史数据一次性迁移由仓库脚本 `scripts/migrate_single_loop.py` 完成，运行内核不导入它。
先停止并排空所选项目服务，再执行 `--apply --backup-root <目录>`。默认只读预演。
脚本移除旧配置开关，把剩余占位节点展开为原始 trace 输出，补齐未知工具结果，
归档私有 v1 检查点到迁移备份。源文件变化或服务仍在运行时拒绝写入；重复执行无变更。
回滚须一起恢复备份中的数据和旧代码，不能只换代码。

停机先停止调度器领取新任务，再等待已领取任务完成并记录结果，随后关闭会话入场并取消、
收尾活动 run。定时任务定义和下次触发时间不因本迁移重建。
