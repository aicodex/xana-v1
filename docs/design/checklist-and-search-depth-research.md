# 搜索深度与清单 / 计划 / 检查点调研

起因：大摩《中国先进封装》测试里，Kimi 调了一次 `web_research`(effort=high,40 页)就直接总结；ChatGPT 对同一问题会做三轮(确认报告 → 找映射公司 → 查公司数据)。同时想借鉴 Kimi Web 端输入框上方的工作栏(计划 / Bash / 后台 Agent / 当前进度 6/6)。原则:不用提示词硬性引导模型多搜,优先改工具与机制。

## 一、为什么只搜一轮

### 1.1 各家怎么决定搜索深度

| 产品 | 做法 | 来源 |
|---|---|---|
| Claude.ai | 系统提示按复杂度分类:单一事实 1 次;中等 3–8 次;更深更广 8–20 次。「请求涉及多个独立项时逐项分开搜,合并成一个查询每项都只拿到表层结果」;「答案每部分都有检索依据才停;写之前逐项核对请求与已检索内容」 | 泄露的系统提示(中等可信) |
| Kimi 网页版 | 「单一事实一轮;越复杂轮数越多,直到来源足以支撑答案」;web_search 默认 1 个查询,真正独立的子话题最多 2 个——**刻意限制单轮并行度,逼出串行多轮**;金融数据先走结构化数据源 | 泄露的系统提示(中等可信) |
| ChatGPT | 只规定何时必须搜;`web.run` 每次 ≤4 个查询,返回带引用 ID 的**原始片段**,要自己 open/find 往下挖;多轮主要来自端到端 RL 训练 | 泄露提示 + OpenAI 官方博客 |
| Perplexity | 「每次调用后评估是否覆盖问题的各子部分,持续到解决」;每次 ≤3 个查询 | 泄露提示 + 官方 API 文档 |
| Anthropic 研究系统 | lead 按复杂度分配:简单 1 个 agent 3–10 次;比较 2–4 个子 agent 各 10–15 次;子 agent 拿到结果后「评估质量、找缺口、改写下一次查询」 | 官方工程博客 |

努力程度参数(官方文档):OpenAI `search_context_size`(low/medium/high,「不保证来源数量」)与 reasoning effort(「改变搜索的深度和延迟」);Anthropic web_search `max_uses`(只有上限)与 `effort`(「effort 越低,工具调用越少越简短」);Perplexity `search_type` fast/pro/auto、`reasoning_effort`;Tavily `search_depth`;Exa `type` instant…deep-reasoning;Kimi `reasoning_effort` low/high/max。**规律:API 的深度参数都作用于单次调用内部;跨调用的轮数交给模型(训练、提示或 effort)。**

### 1.2 我们的问题出在哪(假设)

1. **工具返回像结论**:一次调用就多查询 × 40 页 × 小模型提炼,模型看到"目标已被回答",没有"还缺什么"的信号。业界没有一家把提炼后的结论当单次工具结果给主模型;Search-o1、Claude 动态过滤的提炼都在主模型循环内部、每次只回答当前子问题。
2. **单次调用吞下太多子问题**:这次的 objective 把"报告观点 + 公司名单"打包成一个目标(日志可见),等于把 Claude.ai 说的"合并查询只得表层"做进了工具。
3. **结果里缺少下一步的抓手**:原始片段天然带新实体(公司名、代码、日期),提炼后这些线索可能丢了。
4. **推理强度**:Anthropic 明确说 effort 越低工具调用越少,Kimi 也有 `reasoning_effort`。
5. **缺少计划/清单**:Gemini、ChatGPT Deep Research、Claude Research 都先出研究计划再逐项搜。

没有找到"原始片段 vs 提炼结论"影响搜索轮数的直接实验文献,需要自测。

### 1.3 最小实验(按成本排序)

同一组链式问题(报告 → 映射公司 → 公司数据)3–5 个,每个条件 5 次;指标:工具调用轮数、三个环节是否覆盖、事实错误数。

| 序 | 假设 | 实验 | 改动 |
|---|---|---|---|
| 1 | 推理强度 | 切换 Kimi thinking / reasoning_effort | 无 |
| 2 | 目标打包 | 回放日志,统计 objective 覆盖的子问题数 | 无 |
| 3 | 返回像结论 | 小模型在返回末尾只陈述"按目标未被证据覆盖的部分 / 冲突点",不建议下一步 | 只改工具 |
| 4 | 单次吞太多 | 单次上限降到 ≤3 查询、10–15 页(对齐 Kimi/ChatGPT/Perplexity) | 只改工具 |
| 5 | 缺抓手 | 返回附"新出现的实体 / 待核实数字"列表(带引用,不附建议) | 只改工具 |
| 6 | 提示词基线 | 只加 Kimi 那一句"越复杂轮数越多,直到来源足以支撑答案" | 对照组,不作最终方案 |

## 二、清单 / 计划 / 检查点:三家对比

| 维度 | Claude Code(TodoWrite v1 / Task v2) | Codex(update_plan) | Kimi Code(TodoList) |
|---|---|---|---|
| 结构 | v1:content/status/activeForm,整表替换;v2:subject/description/owner/blocks/blockedBy,逐项增改 | step + status(pending/in_progress/completed)+ explanation,整表替换 | title + status(pending/in_progress/done),整表替换 |
| 状态放哪 | v1 内存(按 agent 分开);v2 磁盘 `~/.claude/tasks/<id>/*.json`,带锁,多 agent 共享、跨进程 | 不存,只发一个事件 | 持久事件折叠成状态,跨轮、跨重启;可撤销(撤销对话时一起回滚) |
| 压缩后 | v1 靠对话记录;v2 在磁盘 | 只靠历史里的调用参数 | 压缩摘要末尾自动附上 `## TODO List` |
| 提醒 | 10 轮未更新注入 system-reminder(2.1.281 可关) | 无 | 10 轮未更新注入温和提醒 |
| 完成前验证 | 2.1.88:一次关 3 项以上且无验证项 → 追加提醒(2.1.281 未见);v2 的 TaskCompleted hook 可拦截标完成 | 无 | 无 |
| 驱动续跑 | **不驱动**(没做完也不拦 Stop;完成度交给 /goal 评估器) | **不驱动**(goal 续跑模板:"未执行的计划不算进展") | **不驱动**(真正控制回合的是 Goal 和 Plan) |
| UI | spinner 显示当前项;TaskListV2 面板 "N tasks (x done, y in progress)" | 对话里插 "Updated Plan";状态栏 "Tasks x/y" | 输入框上方工作栏"当前进度 done/total" |
| 计划模式 | 权限状态机;退出要用户审批;plan 文件;压缩后重新附上 | collaboration mode + `<proposed_plan>` + "Implement this plan?" | 计划模式只允许写 plan 文件;ExitPlanMode 发起审阅(批准 / 修改 / 拒绝并退出);每版计划存快照 |
| 检查点 | 每条用户消息一个文件快照,/rewind 可恢复代码、对话或两者 | ghost snapshot 已删除,只剩回退对话的 backtrack | 按轮撤销对话,可撤销状态一起回滚;文件每轮记 start/end 检查点 |

结论:

- **清单已经是 harness 状态,不只是工具**:状态在工具之外、跨轮跨压缩存活、定期提醒、给 UI 用。Codex 是例外(纯显示工具)。
- **三家都不用清单驱动续跑**。"做完没有"交给独立机制:CC/Codex 的 goal 评估器、Kimi 的 Goal;"做到哪了"交给清单。这与我们已有的判断一致(todo 不驱动续跑,见 turn-control-design)。
- **计划 = 用户审批过的契约**;清单 = 执行进度;两者分开存、分开显示。
- 检查点(回滚)是可撤销状态 + 文件快照,CC 与 Kimi 都做成了一等功能。

## 三、Kimi Web 工作栏

Web 前端在另一个仓库,本仓库只有构建产物;以下来自打包后的前端和 agent-core-v2 后端源码。输入框上方一排胶囊(同一时间只展开一个浮层):

| 胶囊 | 何时出现 | 内容 |
|---|---|---|
| 目标 | 有 goal 时 | 目标、完成标准、状态(进行中/暂停/阻塞/完成),可暂停、恢复、取消 |
| 计划 | 计划模式开启或本会话有过计划 | 审阅状态(待确认/已通过/已拒绝)、选中的方案、用户反馈、计划正文 |
| 后台 Bash / 后台任务 | 有任务时 | "N 运行中";每条:状态、描述、命令、耗时(运行中每秒刷新)、停止按钮;筛选:最近/进行中/已完成/全部;点开看完整输出 |
| 后台 Agent | 有后台子 agent 时 | 卡片网格:名称、模型、状态、耗时、停止 |
| 当前进度 | 有清单时 | "当前进度 done/total",每项状态图标;全部完成换图标 |

数据链路:agent 事件 → 服务端投影成转写操作(task.upsert / todo.upsert / meta.merge)→ 前端快照 → 各面板。**工作栏与对话流里的工具调用是两套视图**:对话流按时间展示每次调用;工作栏展示当前状态(计划、进行中的任务、进度)。

## 四、xana 现状与差距

| | 现状 | 差距 |
|---|---|---|
| 清单 | `todo_write` 工具 + 10/10 提醒(照 CC) | 状态只在工具存储里;不进压缩摘要;不发事件,渠道看不到进度 |
| 计划 | `enter_plan_mode`(权限 mode=plan) | 没有计划文档、没有审批流、没有版本 |
| 目标 | goal 模式 + 独立评估器 + report_goal | 状态没有给渠道显示 |
| 后台任务 / agent | async run、spawn 链 | 渠道只有 run 列表,没有统一的"当前状态"视图 |
| 检查点 | 无 | 无文件快照 / 回滚 |
| 渠道 | 卡片:回答 + 工具块 + 进度行 | 没有"工作栏"这一层状态视图 |

## 五、建议的下一步(待讨论)

1. **搜索**:按 §1.3 顺序先跑 1、2(零改动),再依次试 3、4、5(只改工具返回形态和单次上限),每次一个变量;不加系统提示引导。
2. **清单升级为 harness 状态**:照 Kimi 的做法——清单状态独立存储、跨轮跨压缩(压缩摘要附带)、状态变化发事件;**不驱动续跑**(三家一致)。
3. **工作栏状态模型**:定义一个渠道无关的"会话工作状态"(目标、计划、任务/后台 run、子 agent、清单),由 harness 事件投影得到;飞书/TG 卡片先显示一行摘要(如"进度 3/6 · 后台 2"),以后的 Web UI 做成 Kimi 那样的胶囊 + 浮层。
4. 计划审批与检查点另立设计,排在 2、3 之后。
