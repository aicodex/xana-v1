# 单循环对话与取消机制迁移方案

目标是将同一会话的多 run 分叉、普通占位回填和 attach 切换，收敛为一个活动执行循环，支持用户补充输入和明确取消。独立子任务、定时任务、流式输出及异步 I/O 继续保留。下文记录迁移前的代码盘点与方案；当前源码已实施，生产切换已完成。

参考机制与源码证据见 [Codex 插话机制源码审阅](../../exp_ai/context_codex_steering.md)。首次迁移以完整模型响应及工具结果为插话边界，Kimi 快速采样中断单独验证。

## 建议采用的用户行为

| 操作 | 迁移后的建议行为 |
|---|---|
| 空闲时发消息 | 建立一个 run 和一张回答卡 |
| 回答中补充消息 | 接收并显示待处理状态，进入当前 run；到安全边界后处理，延续同一张卡 |
| 点击取消回答 | 立即确认请求并显示停止中；停止当前 run 的后续模型、工具派发，完成必要清理后显示已取消 |
| 取消后发新消息 | 正常开始处理，旧取消标记不能作用到新 run |
| 点击过期取消按钮 | 只检查按钮原先指向的会话与 run；已结束则无操作，不能改为取消最新 run |
| 后台任务完成 | 活动会话接收结果输入，空闲会话按既有通知意图启动处理；停止过的 run 的关联结果不得自动把该 run 恢复 |
| `/compact` | 安排在当前执行的安全边界；空闲时直接运行。压缩过程可取消，后续输入等待压缩完成 |
| `/clear` 或 `/agent` 切换 | 建议先保持现有换 session ID、旧会话继续完成的行为；旧卡可取消其原 run，结果不会写入新会话 |
| `/tasks`、`/resume` | 保留任务查询与明确续跑，移除 attached 等前后台视图状态 |

这里的“安全边界”包括：本次模型响应已完成、该响应的工具调用都有确定的结果记录，或者等待工具已按正式契约返回任务 ID。普通消息到达不会杀掉正在执行的工作。

取消回答的范围是该 run，以及仍由它直接等待和拥有的调用。已返回任务 ID 的独立后台任务、其他会话和定时任务继续运行；停止它们使用明确的任务取消动作。取消前已接收但尚未消费的用户补充保留为待处理，不静默丢弃，也不在取消后自动发起一轮续跑；下一次用户输入时可见并继续处理。

上述行为在实施前一起确认，尤其是忙时默认补充、取消独立任务的范围，以及清空会话时旧 run 的去留。本文中的建议不等于已更改这些行为。

## 当前代码的耦合与迁移风险

| 位置 | 实际行为 | 迁移要求 |
|---|---|---|
| [serve.py](../../src/xana/cli/serve.py) `_run_inbound_pump` | 每条入站消息建立 task；控制命令也由此进入 | 继续及时接收入站；在会话内部协调，不能把整个渠道 pump 改成逐条等待到回答结束 |
| [gateway.py](../../src/xana/agent_adapter/gateway.py) `_submit` | 新消息 detach 旧 run，再建立新 run；遇到 final/error/cancelled 就退出消费 | 普通消息进入活动循环；执行者拥有 worker 生命周期，渠道消费结束或断连不能使执行悬空 |
| [default.py](../../src/xana/harness_sdk/default.py) `_invoke` | 同步和异步都 fork、放普通 PH，完成后回填；同步开关只改变消费方式 | 不能靠 `async_mode=False` 完成迁移，要改为向同一会话历史逐步提交已完成过程 |
| 同文件 `_run_query_loop` | 记忆召回和输入扩展每个原始请求执行一次；Stop 决策可能结束 run | 每条显式补充执行必要的输入准备；检查待处理输入后再收尾，不重复 turn 生命周期钩子 |
| [chat_agent.py](../../src/xana/agents/chat_agent.py) `cancel` | 无 run ID 时设置下轮生效的 `_pending_cancel_sessions` | 删除“取消下一轮”语义；按钮必须精确指向活动 run，取消和输入准入通过同一权威协调 |
| `default.py` 模型流循环与 [kimi.py](../../src/xana/llm_driver/providers/kimi.py) | 取消在收到新流事件后才被检查；provider `cancel()` 是 no-op | 硬取消必须能唤醒等待中的读取、退避和压缩，不能依赖下一条 token；不要误以为调用 provider.cancel 即有效 |
| [run_context.py](../../src/xana/harness_sdk/run_context.py) | 保存私有 prompt、原始产出，承担首次主历史压缩、后续局部压缩及检查点恢复 | 删除前要替换它承担的压缩与恢复能力，不能只删除 fork |
| [main_writer.py](../../src/xana/memory/main_writer.py) 与 [write_queue.py](../../src/xana/memory/write_queue.py) | MainWriter 串行化写入；第二个队列仅消费 PH 替换 | 保留单一写入所有者的作用，删除 PH 专用队列和 consumer，避免再造两套写回通道 |
| [background.py](../../src/xana/harness_sdk/background.py) | task_wait 等待本身有 shield；agent_run 在等待被取消时会停止子任务；结果按父 run 状态分流 | 插话唤醒必须与 task.cancel 分开，否则会误杀子 agent；后台完成结果统一进入输入准入 |
| [delivery.py](../../src/xana/runtime/delivery.py)、[scheduler.py](../../src/xana/runtime/scheduler.py) | 通知最终走 gateway.submit；定时任务在独立子会话执行 | 通知在会话忙时不能再建立竞争 run，定时执行本身继续独立 |
| [unified_card.py](../../src/xana/agent_adapter/channels/unified_card.py) 与渠道 renderer | 顶部同时有取消回答和后台回答；无显式 action 的按钮被当成 detach | 删除 detach 默认动作，保留独立取消动作；完成事件不再依赖 ph_replaced |
| [xanac_textual.py](../../src/xana/cli/xanac_textual.py) | 前后台 tab、attach 回调；部分状态使用 session ID 充当 run ID | 删除 run 切换；严格使用服务端回执中的真实 run ID |
| [file_store.py](../../src/xana/session_config/file_store.py) | `SessionConfig(**data)` 严格加载持久字段 | 删除字段前先迁移配置，否则旧 async_mode 会使加载报错 |
| [startup_scan.py](../../src/xana/state/startup_scan.py) 与 [file_history.py](../../src/xana/memory/file_history.py) | 修复或替换 PH，检测中断并可能加入 Continue | 迁移后按 run 和输入状态恢复，停止重新创建 PH；用户取消不能因历史尾部是 tool/user 而被误当成自动续跑 |

还有两处必须保留的能力：`DefaultHarness._background_tasks` 同时跟踪后台记忆提取，不能整段删除；`tool_batches.run_batch` 在生成器关闭时取消未完成调用，插话不能用关闭它的办法获取控制。

## 协调状态与正式契约

每个 session 只有一个活动 run 所有者，覆盖 gateway、`AgentRunner`、resume 和通知入口；不同 session 可并行。协调器只需一个具体实现，使用类型化依赖，由 boot 统一组装，不为它新增 ABC，不再经 metadata 注入控制服务。

输入内容复用现有请求与媒体契约，补充必要的消息 ID、接收顺序、来源和目标 run 标识。准入回执区分开始、已接收补充、已过期或拒绝，不能用 HTTP 202 或 SSE 序号代替模型消费确认。初始 agent、模型和权限配置在 run 内保持一致，补充消息不能借新一次 mapper 调用静默改变它们；配置修改作用到下一个 run。

会话内执行状态至少区分空闲、准备输入、模型调用、工具执行、压缩、停止中和收尾。控制动作不排在普通输入队列后等待；取消、输入准入和收尾决定在同一协调点排序。收尾持久化后再次检查晚到输入，关闭与开下一轮必须原子决定。

执行 worker 的生命周期由服务拥有。SSE 订阅与重连只是观察，不触发模型执行，也不取消模型执行；可保留现有流订阅端点，无需保留业务上的 attach/detach。

接收队列持久化与已应用历史要通过正式状态接口协调，使用稳定消息 ID 做幂等提交：先持久接收再确认，应用历史成功后再标记已应用，失败重启时能确定是否已写入。只保留一个输入状态权威，不能另建一份影子业务队列；模型是否已消费要与具体请求关联，禁止在未知响应状态下自动重放有副作用的工具。具体字段在实施前统一更新现有 state/harness 合约。

## 执行和取消的边界

普通补充先加入队列。当前响应及其工具结果处理完整后，按接收顺序应用补充、准备记忆召回和输入扩展，再检查上下文预算、压缩并请求模型。输入准备包含媒体导入、当前模型能力校验和 agent 的技能/工具范围；不能把补充当纯文本直接插入而绕过这些规则。

同一 run 的工具轮编号、预算、usage 和 episode 状态连续累计，不随插话重置。生命周期钩子仍按 run 调用一次，逐消息输入贡献单独调用；记忆提取按明确消息边界包含全部补充，避免依靠原始输入字符串寻找最后一条 user。

`AbortSignal` 增加可等待的取消通知。模型读取在运行任务中同时等待流事件和取消通知；取消时由持有流的任务清理读取并关闭自身响应，不能关掉共享 HTTP client。关闭后的流不得被当成网络故障自动重试，也不得执行未确认完整的工具参数。

硬取消后不派发新工具；尚未执行的已记录调用补明确的未执行结果，已执行调用保留真实结果。当前工具保留现有协作取消与写操作宽限规则，完成配对和状态记录后再结束。收尾需等取消传播和必要的 task 清理；UI 可先显示停止中，不能先宣布停止再让本地工具继续执行。

插话的唤醒通知与硬取消信号分离。`task_wait` 或 `agent_run` 正在等待时，优先使用已有 BackgroundTasks 让等待返回 running + task ID，子任务继续。普通 Bash、命令工具暂时等待其结果；本次不同时引入一套通用 code-mode 或可恢复进程系统。Kimi 的无 token 流硬取消必须完成，快速插话打断其半段生成可后续单独评估。

取消前尚未消费的补充与当前 run 的关联结果保持可查询。停止本 run 后不因这些旧输入自动重开它；后续新的用户请求可正常进入，不继承取消标志。独立定时通知遵守自己的触发意图，不被一次对话取消永久禁用。

## 压缩和恢复的替换

压缩仍由每会话唯一执行者串行安排。手动请求在模型/工具安全边界进行；自动压缩和手动压缩复用同一操作。生成摘要期间的新输入留在待处理队列，不改变被冻结前缀。

用冻结的行 ID/前缀版本提交摘要：先生成完整转录档案，再持久提交摘要和覆盖范围，最后更新内存；失败不覆盖原历史，提交开始后完成原子发布再释放执行权。复用 `HistoryMirror.compaction_prefix/compact` 的现有匹配语义，替换 SDK 的 PH 插入及 collapse 操作，不做无条件 set 整个上下文。

保留多模态分批摘要、摘要输出上限、原始媒体引用、revealed tools、上下文预留公式及实际 usage 校准。本次不启用闲置工具结果清理，也不重新调整模型预算参数。

新 run 过程逐步提交主历史与原始 trace。恢复依据已持久提交的消息、输入状态和工具配对：结果未知时明确记录未知，不自动重执行。`/resume` 继续已完成过程，不能重新追加原始 user 请求再从头执行。旧 v1 私有检查点先在迁移工具中转换或归档，生产运行链不保留第二套旧引擎。

## 分阶段迁移路径

阶段是可独立验证的开发单元，线上继续运行原版本，完整迁移通过后再统一切换；不增加长期共存的旧模式或新开关。

| 阶段 | 具体工作 | 通过条件 |
|---|---|---|
| 1 确定行为和冻结基线 | 确认本文行为表；记录安装基线与工作区差异；在数据副本上生成配置、PH、检查点迁移清单；建立关键行为回归 | 能解释每类旧数据的去向；不变更生产文件或停止服务 |
| 2 统一执行与持久化 | 建立唯一活动 run 协调；硬取消通知；主历史逐步提交；改造压缩和恢复；去掉普通 PH、RunContext 及回填 consumer | 单会话无并发模型循环；取消静默流可生效；历史、压缩、重启和预算回归通过 |
| 3 接入补充与独立任务 | 逐消息输入准备；安全边界 drain；task_wait/agent_run 提前交还等待；调度和后台通知接同一准入 | 多条补充不丢不重；等待可唤醒但任务继续；完成与收尾竞态不额外启动竞争 run |
| 4 同步渠道与删除旧入口 | 飞书、TG、daemon、Textual、oneshot 和命令同步；取消按钮绑定真实 run；移除 attach/detach、async 配置和 PH 展示字段；更新文档测试 | 渠道无旧动作和默认 detach fallback；端到端取消、订阅重连和下一轮正常；旧入口扫描清零 |
| 5 离线迁移和受控发布 | 副本演练通过后封闭项目准入、等待现存执行收尾、备份、迁移、检查再启动 | 无未核对执行；数据迁移幂等；服务健康、模型预算、调度配置和历史完整性验证通过 |

阶段 2 到 4 若需要本地临时适配，只限开发过程，切换前删除，不作为生产兼容契约。既有规范 [session-and-card-state](session-and-card-state.md) 在最终实现时原位更新为新契约；旧规范归档移出默认阅读路径，不能与新规范同时声称唯一权威。

## 数据迁移与部署操作

迁移工具先 dry-run 输出逐文件变更和数量。879 份旧会话配置只移除 `async_mode`，保留其他字段；重新扫描获得实际数量。主历史中已回填完成的消息保持原顺序和身份，已 compact 的摘要与档案不展开、不重压缩。

对残留 PH，按原位置取回对应 run trace 的已确认完整消息，补工具结果未知标记，移除普通 PH，将未完成任务保持暂停。已完成 marker 与 RunRecord 矛盾时停止自动处理并报告，不能猜测。保留原始 trace、检查点、compact 档案、媒体和损坏源行；本次扫描无解析错误，工具仍须有拒绝未知格式的行为。

迁移记录输入文件哈希、备份路径和结果标记，重复运行不得重复插入过程或补充消息。转换后的生产读取器只接受当前格式；格式识别失败明确报错，不静默切回旧实现。历史 v1 检查点若需要恢复，转换必须验证来源 run/session 与工具配对；不把其他分支的私有摘要直接覆盖当前主历史。

上线前重新核对进程内活跃 run、独立任务和调度器在途 dispatch，不能仅看历史 RunRecord。先阻止新的 dispatch 领取到期任务，再等待已有 dispatch 完成；调度器 `pop_due` 会提前移除一次性任务或推进 next_fire，所以不能只等 gateway 空闲便停止服务。未结束工作先等完；确需中止时另行报告，不以强杀完成迁移。

本次切换期间暂停领取的到期任务须保留，启动后按既有调度规则领取，并核对一次性任务及触发历史。备份至少包含代码版本、项目配置、会话配置、主历史、run 元数据与 trace、检查点和任务登记文件；媒体采用原文件保留与引用校验。离线迁移按项目执行，未通过检查不启动新执行器。

回滚不能将有新写入的会话目录直接换回旧备份。新版本接受真实输入前可恢复原快照；接受后须保留新增历史，停止准入并按具体格式制定逆迁移，避免抹掉刚产生的结果。

## 验证矩阵

| 场景 | 必须证明 |
|---|---|
| 模型一直不发 token 时取消 | 控制可被立即接收；读取被唤醒并清理；下一条用户消息正常 |
| 当前工具执行时取消 | 无新增副作用调用；已完成结果保留；未完成结果准确标记；宽限后收尾 |
| 连续补充、多媒体补充 | 消息顺序和身份稳定，能力校验有效，不重置预算，不建立第二个前台 run |
| task_wait/agent_run 等待时补充 | 等待返回任务 ID，子任务继续；真正停止子任务仍需明确动作 |
| final、输入与取消竞态 | 一个终态、一次钩子；无接收后漏处理；旧取消不影响新 run |
| 压缩期间补充或取消 | 冻结前缀匹配、失败不丢历史、转录和媒体可回查、重启不重复摘要 |
| 准入、历史提交、工具前后各点崩溃 | 输入可恢复且不会重复执行未知副作用；/resume 不重复 user 或产出 |
| 飞书/TG 按钮、daemon 与 Textual | 按钮带正确归属；TG 不截断控制标识；旧卡、跨会话、重连均不误取消 |
| clear、agent 切换与定时结果同时发生 | 各会话状态隔离，旧执行不写入新上下文，结果投递到既定目标 |
| 调度到期遇到停机 | 在途 dispatch 有归属，一次性任务不因切换丢失，配置和触发历史可核对 |

已运行现有基线：`test_gateway_cancel_triggers_live_signal.py`、`test_gateway_early_exit.py`、`test_compact_resume_integration.py`、`test_background_tasks.py`，20 项通过。这些证明当前相关机制可作为回归基线，不证明新机制已实现。

实施验证先跑对应模块与上述矩阵，再跑架构检查和完整离线回归；真实模型验证只做必要的小规模 Kimi 请求、工具等待及渠道按钮检查，不重新执行 demo 的整条视频生成流程。
