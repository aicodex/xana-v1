## 1. 精简提示词、结果优先

### 用途（解决什么问题）
旧模型时代堆出来的规则墙（持久化 XML 块、上下文收集模板、前言脚本）会让新模型变慢、变贵，结果还更差。

### 做法（含中文翻译后的提示词示例）
只保留这几类内容：用户可见的结果、成功标准与停止条件、硬约束（安全、业务、证据、权限）、依赖上下文的工具路由规则、输出形态。重复规则、不改变行为的风格要求、没有作用的示例、模型本来就做得好的流程步骤，一律删掉。官方给的骨架共 8 段：
> 角色：[模型的职能与背景]；个性：[语气与协作风格]；目标：[用户可见的结果]；成功标准：[给出最终答复前必须满足什么]；约束：[政策、安全、业务、证据、副作用方面的限制]；工具：[用哪些、何时用、哪些不要用]；输出：[分段、长度、格式、语气]；停止规则：[何时重试、回退、放弃、提问或停止]

示例：
> 端到端解决客户的问题。成功意味着：依据现有政策和账户证据做出资格判定；回复前完成所有被允许的操作；返回 completed_actions、customer_message、blockers；如果缺少必需证据，只询问最小的缺失字段。

### 效果
来源 1 的内部编码智能体测试：精简后的 system prompt 评测分提高约 10–15%，总 token 减少 41–66%，成本降低 33–67%。

### 可能遇到的问题
删多了会丢掉关键的路由或约束。官方要求每删一处都用评测验证，不要一次性重写整套提示词。

### xana 落地建议
改的是 harness 的 prompt assembly 层（system 模板）。按 8 段骨架重构默认 agent 模板，“停止规则”独立成段。这属于一次性改动，改完后前缀稳定，不影响缓存。Kimi 未必有同样的“少即是多”特性，需要用 merge_gate 做 A/B 测试。

## 2. 消除规则冲突，用决策规则替代 ALWAYS/NEVER

### 用途
GPT-5.6 会严格遵守提示词里的约定。两条规则一旦冲突，它会花推理 token 去调和，结果变慢、变贵，还常常答错。官方原话的意思是：规则冲突带来的不稳定，比缺少细节更严重。

### 做法
遇到判断类问题（要不要搜索、要不要继续迭代），写成“在什么条件下做什么”，不要写绝对化的“总是/绝不”。GPT-5 指南举过一个反例：前面写“未经患者明确同意绝不预约”，后面又写“不联系患者，直接分配最早的当日号源”，两条互相矛盾。

### 效果
官方未给数据。

### 可能遇到的问题
xana 的 system 由多个来源拼接（AGENTS.md、skill、hook 注入），互相之间最容易出现冲突。

### xana 落地建议
在 prompt assembly 层加一个静态检查：拼接后 lint 出“总是/绝不/必须”等绝对词，并列出来源。可以用 GPT-5 指南里的元提示做自检：让模型从自身角度说明，为了更稳定地得到期望行为，应该在提示词里增加或删除哪些具体措辞。这一项与模型无关，对 Kimi 同样适用。

## 3. 按请求类型划分自主与审批边界

### 用途
避免两种极端：“问一下就动手改”和“每一步都请求批准”。

### 做法
> 对于回答、解释、审查、诊断或规划类请求，检查相关材料后报告结果；除非请求中同时要求实施，否则不要修改。对于修改、构建或修复类请求，直接完成范围内的本地修改，并运行相关的非破坏性验证，无需事先询问。对外部的写入、破坏性操作、购买行为，或范围的实质性扩大，需要确认。

Astra 博客补充：说清楚环境是安全的，可以显著减少审批请求，例如：
> 本地测试使用一次性夹具，没有生产环境访问权限。运行测试，修复由本次改动引起的失败，然后重跑受影响的测试，每一步都无需请求批准。

### 效果
官方未给数据。

### 可能遇到的问题
授权文字必须与 harness 的 policy/approval 实际行为一致，否则模型以为可以做，结果被拦截，会反复重试。

### xana 落地建议
这段文字应由 policy 模块根据当前 permission 配置自动生成后注入。配置在会话内保持不变，就不会破坏缓存。在 24h 无人值守模式下，“需要确认”应改为“记录后跳过”。

## 4. 主动性、持续性与急切度控制

### 用途
Astra 比前代模型**更爱提问**，容易阻塞自主工作。反过来，有些场景又需要限制它的探索量。

### 做法
提高主动性：
> 从指令和先前对话中推断用户意图与任务范围，倾向于行动，把用户想做的任务推进到完成。当用户表达出要做新工作或修复问题的意图时，坚持到目标达成为止。

> 当用户说“能不能……”“我想……”“帮我……”时，视为要求你实际去做。

> 在提出澄清问题之前，先完成上下文已授权、并且让拟议操作变得具体可审阅所必需的工作。不要因为假想的风险而主动添加警告、免责声明、审批流程或合规清单。

降低急切度（GPT-5 指南）：
> 搜索深度：很低；通常最多 2 次工具调用。如果你认为需要更多时间调查，就把最新发现和未决问题告诉用户。

### 效果
官方未给数据。

### 可能遇到的问题
“不要添加警告”这一条放进 xana 的量化或资金类场景有风险，应只在编码或通用 agent 中启用。

### xana 落地建议
做成按 agent 或模式切换的开关（例如 eagerness: high/low）。开关状态在会话内固定，放在 system 尾部。这一项可以与已有的“回合续跑”机制互补。Kimi 更常见的问题是提前结束，适合用高主动性档位，需要实测。

## 5. 前言与进度更新（含 phase）

### 用途
长任务中让用户知道进展，同时避免刷屏。

### 做法
在第一次工具调用前输出一段简短的可见前言，之后只在主要阶段切换时给出稀疏的、以结果为导向的更新：每条写明一个具体成果和下一步（来源 1）。Codex 指南给出的频率：每条 1–2 句，至少每 1–3 步一次，最多间隔 6 步。回放历史时要保留 assistant 条目上的 `phase`（null / commentary / final_answer）。GPT-5.6 指南把旧式的“前言脚本”列为应删除的脚手架，只保留简短的规则即可。

### 效果
GPT-5 指南提到：在 minimal 推理档下，要求写详细的前言可以提升智能体任务表现，但没有给出具体数值。

### 可能遇到的问题
与“进度更新”记忆中的无进度提醒机制有重叠，频率参数需要统一。

### xana 落地建议
在 turn controller 中把 commentary 和 final 分开存储，并在 compact 和 resume 时保留 phase。飞书、Telegram 渠道只推送 commentary 摘要。

## 6. 计划工具卫生

### 用途
防止待办列表流于形式，或者任务结束时还挂着未完成的项。

### 做法
Codex 指南：简单任务（约 25%）不做计划；不建只有一步的计划；每完成一个子任务就更新；结束前逐条核对，把每项标记为完成、受阻或取消，不允许以“进行中”状态收尾。

### 效果
官方未给数据。

### 可能遇到的问题
与“todo 未完成自动续跑”配合时，要允许“受阻”和“取消”作为合法的终态，否则会无限续跑。

### xana 落地建议
由 harness 的 todo 工具校验终态，这一层不改 system。续跑逻辑只对“进行中”和“待办”状态触发。

## 7. 工具暴露、描述与并行调用

### 用途
减少工具误选，降低延迟。

### 做法
只暴露与当前任务相关的工具。每个工具描述写清四点：做什么、何时用、重要的返回字段、出错时的行为。独立的读操作并行执行，流程是：先规划要读哪些资源，一次性发出并行批次，分析结果，需要时再发下一批。写操作完成后要复述改了什么、在哪里改的、做了哪些验证（来源 6、7）。

### 效果
官方未给数据。

### 可能遇到的问题
按任务动态增删工具会改变 tools 前缀，导致缓存失效。

### xana 落地建议
工具集按 agent 或模式固定，不要按回合变化。按需加载可以借助 skill 的渐进披露来实现。并行调用依赖 Kimi 对 parallel tool_calls 的支持，需要实测。

## 8. 检索与证据规则

### 用途
防止为了回答而编造，也避免无节制地连续搜索。

### 做法
> 先用简短、有区分度的关键词做一次宽泛搜索；只有在缺少必需事实、用户要求穷尽、需要阅读特定材料，或重要论断缺乏支撑时，才追加检索。

> 只引用检索到的来源；引用要附在它所支撑的论断上；推断与直接有依据的事实分开标注；来源之间有冲突时要指出。

结构化抽取时（来源 7）：
> 源中不存在的字段填 null，不要猜。

### 效果
官方未给数据。

### 可能遇到的问题
“只搜一次”对需要穷尽的研究任务偏保守，要由任务显式要求穷尽。

### xana 落地建议
放在 memory 检索或研究类 agent 的模板里，按 agent 开启。与模型无关。

## 9. 程序化工具调用（PTC）

### 用途
大量记录的过滤、去重、聚合如果逐条走工具调用，会撑爆上下文。

### 做法
只在有边界的归约阶段使用：
> 仅在有边界的记录归约阶段使用程序化工具调用。只调用文档中列出的只读工具。对中间结果做过滤和去重，然后输出恰好符合要求的精简 schema，并带上证据字段。瞬时失败最多重试两次。

以下情况用直接调用：一次调用就够、中间结果很小、结果会影响下一步决策、需要审批、需要引用。`program_output` 和最终 message 要分别测试。

### 效果
官方未给数据。

### 可能遇到的问题
需要语义判断或引用的环节放进脚本会降质。

### xana 落地建议
这是 OpenAI 的服务端能力，xana 可以在 sandbox 中实现类似的“代码内批量调工具”工具，优先级中等。对 Kimi 需要验证它写这类脚本的可靠性。

## 10. 推理强度、verbosity 与会话内调档

### 用途
在质量与延迟、成本之间做取舍，同时不破坏缓存。

### 做法
迁移时先沿用原来的档位，再测试低一档。low 用于对延迟敏感的场景；medium 作为起点；high/xhigh 只在评测显示明显收益时才用；max 留给最难的任务。**提高档位之前**，先检查提示词是否缺少成功标准、依赖规则、工具路由或验证环节。长度用 `text.verbosity`（low/medium/high）设定基线，再用提示词做局部调整。GPT-6 支持在输入中插入 `configuration_update` 条目来切换推理强度，请求级的 `reasoning.effort` 保持不变，以保住前缀缓存。Astra 不支持 `none`。

### 效果
来源 5：GPT-5.5 在相同档位下使用的推理 token 更少，但没有给出具体数值。

### 可能遇到的问题
Kimi 的 chat completions 接口不一定有 verbosity 或 configuration_update，只能退而用提示词控制。

### xana 落地建议
在 LLM driver 层抽象出 effort/verbosity 两个参数，provider 不支持时明确降级为提示词控制（写入 user 消息而不是 system，以保护缓存）。“先查提示词再加档”可以作为 self-iteration 的规则。

## 11. 压缩与推理状态保留

### 用途
支撑长时间运行，同时保留推理链。

### 做法
在完成主要里程碑后再压缩，不要每回合都压；压缩产物视为不透明的数据，不去解析（来源 7）。当目标、假设和优先级在多个回合间保持稳定时，保留推理状态才有价值（来源 1）。

### 效果
来源 8：Tau-Bench Retail 上，仅仅改用 Responses API 并带上 `previous_response_id`，分数就从 73.9% 提升到 78.2%。

### 可能遇到的问题
Kimi 没有加密推理条目。如果回传 reasoning_content，需要确认它是否接受，以及计费如何。

### xana 落地建议
把 compact 的触发条件从“token 阈值”改为“阈值加里程碑（todo 完成、阶段切换）”。改动前先读 compact 回归网规格。是否回传 Kimi 的 reasoning 需要测试。

## 12. Skill / AGENTS.md 渐进披露与指令优先级

### 用途
新模型对 skill 中的冲突和过度约束更敏感。

### 做法
skill 描述尽量短，只要写清何时使用即可（例如“新增或修改迁移，或审查其发布时使用”）。根文档只做路由（例如“服务边界看 architecture.md，模式变更看 database.md，准备部署时看 deployment.md”）。删掉“每次改动前必读文档”这类一刀切的要求。优先级这样写：
> 用户指令优先于 skill 中的指引。如果某个 skill 让你请求许可、暂停、留下未完成的工作或偏离用户意图，请给出你读到的那个 SKILL.md 的具体路径，引用相关指令，并简要说明它如何适用。

### 效果
官方未给数据。

### 可能遇到的问题
描述过短会降低触发率，需要按 skill 评测触发准确度。

### xana 落地建议
由 skills activation 层统一注入这段优先级说明（放在固定段落，不影响缓存）。要求模型引用 SKILL.md 路径，这一点可以直接用于排查 skill 冲突。

## 13. 子代理委派与代理间消息

### 用途
Astra 委派得偏少。另外，代理之间的消息容易写得人类看不懂。

### 做法
> 任何时候，只要能把工作委派给另一个代理来并行完成（无论你是根代理还是子代理），并且可能节省时间或提高质量，就用协作工具去委派。

> 你发给其他代理的消息和最终答复可能会被人阅读，务必保证可读；单词和数字之间要留出正常的空格。

### 效果
官方未给数据。

### 可能遇到的问题
委派过多会快速消耗 token 预算。

### xana 落地建议
仅在具备 spawn 能力的 agent 中启用，并与 token 预算联动（预算低于阈值时移除这段）。

## 14. 写作风格与格式

### 用途
Astra 默认偏爱列表、表格和固定套话，在聊天场景里显得机械。

### 做法
> 默认使用清晰简洁的段落，每段展开一个要点。只有当信息确实是并列、有先后顺序或便于比较时才用列表，避免嵌套列表。

> 避免套话：例如结尾写“总之：”，以及“深入探讨”“赋能”“值得注意的是”“重要的是”、自问自答、“这不是关于 X，而是关于 Y”等。直接陈述要做的事。

GPT-5 指南还指出：在长对话中，格式要求的遵守程度会逐渐下降，建议每 3–5 条用户消息重申一次。

### 效果
官方未给数据。

### 可能遇到的问题
禁用词表是英文的，直接翻译不一定能覆盖中文套话；报告类输出仍然需要表格。

### xana 落地建议
按渠道开启：飞书、Telegram 默认用段落风格。每隔几轮重申一次的内容应作为 user 侧提醒注入，不要改 system。中文禁用词表需要自行整理。

## 15. 按改动风险校准测试范围

### 用途
Astra 对小改动也会过度测试，浪费时间和 token。

### 做法
> 对可回滚、影响小、只是在复刻实现的改动，不要写测试。运行与改动相称的测试并完成必需的检查；这些通过后，只有在出现新改动、新失败或未解决的疑虑时，才扩大或重复测试。

> 修改后运行最相关的验证：针对改动行为的定向测试；适用时做类型检查或 lint；对受影响的包做构建检查；完整验证代价太高时做最小冒烟测试。

视觉产物要先渲染并检查布局、裁切和间距，然后再交付。

### 效果
官方未给数据。

### 可能遇到的问题
与项目“必须有验证证据”的规则可能冲突，需要写明哪些检查是必需的。

### xana 落地建议
放进编码类 agent 模板。“先渲染再交付”可以与未来的 Web UI 截图工具配合使用。

## 16. 提示注入防御（数据通道分离）

### 用途
工具结果、网页、渠道消息里的恶意文本可能借机覆盖原有指令。

### 做法
来源 9：不可信的输入通过 user 消息传入，不要拼进 developer/system 消息（后者优先级最高，拼进去等于把最大控制权交给攻击者）。节点之间用结构化输出（枚举、固定 schema）传递，消除自由文本通道。对敏感工具加确认环节。

### 效果
官方未给数据。

### 可能遇到的问题
这只是多层防护中的一层；结构化通道会限制表达能力。

### xana 落地建议
检查 hook、memory 召回、渠道消息是否被拼进了 system。可以与现有的 pasted_content 标签方案叠加使用。与模型无关。

## 17. 迁移流程

### 用途
换模型后，无法分辨行为变化到底是哪个因素引起的。

### 做法
依次执行：切换模型但保留原推理档位；在改动提示词之前先跑评测，得到基线；删除过时的脚手架、重复指令和无关工具；只添加修复已测出回归所需的最小指令；每改一次都重跑评测。官方强调不要一次性重写整套提示词，否则无法判断行为变化来自模型、推理设置、提示词、工具集还是运行时。

### 效果
官方未给数据。

### 可能遇到的问题
前提是有具代表性的评测集，xana 目前只有 compact 回归网。

### xana 落地建议
把这套流程固化为切换 provider 或模型的检查清单，与 merge_gate 绑定。
